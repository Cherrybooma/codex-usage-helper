# 项目管理工作台

用量小助手的桌面胶囊是项目管理入口。Notion 保存项目目标、下一步、任务和产出文档，本机账本记录 Token 投入。采用 Linear 的轻量方式：目标简短、行动具体，进展能打开成果核查。看板让人快速判断现在在推进什么、下一步做什么；Token 不代表完成进度、收益或执行时间。

## 首页的五部分

保留用户指定的五部分顺序；愿景始终在首位。首页使用 Notion 原生页面图标、标题和筛选后的关联视图，完整字段留在数据库和项目详情中。

| 区域 | 人在这里看什么 | 推荐视图 |
| --- | --- | --- |
| 愿景 | 为谁解决什么问题，预期得到什么结果 | 页首项目图标、项目名称和一小段愿景 |
| 待人工确认 | 要决定／验收什么、推荐什么、会影响什么 | 紧凑轻卡片；主 Tasks 视图只筛选待确认 |
| 当前进展与下一步 | 当前阶段、实际完成结果与产出文档、下一行动与风险 | 原生双栏，关联少量未完成 Tasks |
| 历史开发事件 | 什么时间做了什么、产出了什么、入口在哪里 | 近期 Events 紧凑列表、完整历史入口和可展开时间线，关联 Project 与 Tasks |
| 每项目 Token 投入 | 各项目的已记录投入与计量质量 | Usage Daily 关联视图，筛选 Included 为 true |

项目页可进一步放目标与验收标准、关联任务、阶段产出索引、最近复盘、用量视图。使用少量一致的颜色表达状态与风险，不为每个字段加大段说明；原始摘要键、绑定字段和匿名数据集只留在审计视图。

单项目工作台不再放同名 Project 卡重复页面标题，直接展示阶段、完成事实和 AI 下一行动。多项目入口才使用项目卡浏览各项目。首页结构以这五部分为准，不用其他管理方法替换。

“当前进展与下一步”左栏放阶段、完成事实和近期产出入口，右栏突出下一项动作、完成条件与风险。待确认卡片只保留当前决策；用户已经选定的方案写入记录和开发事件，不继续占据待确认区域。历史列表展示近期记录，长说明与完整历史放详情。连接器不支持原生分栏时，应明确尚未落地，不能把文字写成“两栏”就宣称完成布局。

Notion 官方专门的 Dashboard view 目前要求 Business 或 Enterprise。当前结构可使用普通页面、分栏与关联数据库视图，不依赖付费 Dashboard view。布局参考与使用条件见 [官方 Dashboard 说明](https://www.notion.com/help/dashboards)。

## 项目、任务、用量分别记事实

Projects 是管理总入口，Tasks 是具体行动项，每个任务应只归属一个项目；Events 保留开发历史，Usage Daily 是关联投入。项目名称变更不会改变页面身份或本地绑定。

- **项目**：图标、目标、状态、本周目标、下一步、优先级、健康度、交付日期、最近复盘、摘要和阶段产出入口。
- **任务**：所属项目、状态、优先级、日期、管理者、验收标准、对应产出与结果依据。
- **事件**：时间、实际动作与结果、产出与验收证据、项目和任务关系。每次实际推进追加，重复操作按 Event Key 去重。
- **用量**：日期、Codex、计数、统计质量、来源和精确截止时间。当前计入的投入使用 Counted Tokens，不能把旧分配的审计数再加一次。

任务的待办数包含受阻任务，因此待办与受阻不能相加。不将“用了多少 Token”换算成“完成多少项目”。未配置任务源或查询不完整时不编造完成率。

已完成 Tasks 行保留，可由当前行动视图筛掉；开发历史独立追加到 Events。修正结果、重开任务或状态回退，都追加说明事件，不能覆盖旧事实。旧证据的原完成时间未核实时，记录此次回填时间并明确说明，不能填一个看起来合理的历史日期。

阻塞不一定需要人：AI 能自行解决的问题留在当前行动或风险。只有确实需要人的选择、验收或行动，才形成待确认项。无需为这个分类强增数据库字段。

Events 由同项目单写者顺序维护，创建后按 Event Key 复查。该富文本键没有唯一约束，先查后建不保证并发唯一；出现多条同键记录或结果不确定时暂停同键追加并标为待核实，保留历史，不自行删除或合并。

属性约定、图标校验、任务源兼容性与同步方法见 [Notion 连接说明](notion.md)。

## 进展与产出文档相连

每个阶段回答三个问题：**产出是什么、放在哪里、实现了哪些功能或通过了哪些验收。** “做了 UI”“完成开发”是活动描述，需要补上成果才能用于判断进展。

默认在当前阶段下用一张紧凑产出表，复用已存在的 Notion 文档、验收页或实际发布链接，不另建一套 Outputs 数据库。已有合适的 Artifacts 库可以复用。首页只显示近期相关项，完整索引与材料放项目文档。

| 记录位置 | 怎样关联同一产出 |
| --- | --- |
| Project | Outcome 或正文阶段产出索引，摘要说明已实现的功能与剩余限制 |
| Tasks | Evidence 和正文中的成果入口、完成条件与实际验收结果 |
| Events | Evidence 指向同一入口，Result 记录本次变化、实现内容和未核实部分 |

本机尚未推送的成果标为“本机待发布”，只写相对项目路径与结果摘要，例如 `widget/preview/demo.html`，不伪造 GitHub 或可下载 URL。已有授权的 Notion 产出索引可作为入口，但其中必须说明本机文件还未发布。后续发布再补真实链接；原始日志、代码、对话、工具输出、绝对私人路径和认证信息不进入 Notion。

查阅成果时应能从项目到产出，再到对应任务与开发事件。文档复用同一入口，避免每次推进复制全文或建立重名页面。

## AI 协助维护

已有本机项目可以一次整理并导入：调用 Skill 读取实际愿景、计划、实现和产出，生成 `project-import.json`；在项目与 Notion 设置中选择清单和直接子项目文件夹，点击「一键导入项目」。已有管理主页面与库复用；首次配置可以在已共享容器下建立主页面。导入程序不自己生成 AI 结论，不从清单接收任意 Token 数；完整流程见 [Notion 一键导入说明](notion.md#一键导入已有项目)。

目前 Codex 通过 [notion-project-workbench 技能](../skills/notion-project-workbench/SKILL.md)在用户安排的任务中更新项目、Tasks 和 Events；人也可以在 Notion 手动编辑。技能先读取父页面和现有数据源，再复用相关页面与库，不重新初始化成另一套工作台。桌面后台只读取管理信息、更新本地缓存和同步用量摘要，不会自动生成新的项目计划、修改目标或完成任务。

尚未配置持续定时执行的 Notion Custom Agent。普通 Notion Agent 是按需使用，Custom Agents 才支持触发与定时后台运行；是否启用属于后续独立配置。[官方区别说明](https://www.notion.com/help/category/custom-agents)。

AI 更新项目时应遵循这些约定：

1. 从用户目标、实际执行结果和可核查依据创建行动项，避免只有模糊的“继续优化”。
2. 填写明确的下一步；日期和负责人未知时留空，不自行作出承诺。
3. 需要验收的任务先标待确认；已完成应写明产出、入口与实现／验收范围。Token 增长不能作为完成证据。
4. 阻塞应写明问题和所需行动；用 Health 表达项目风险，保留项目本身的生命周期状态。
5. 复盘时写当前状态、行动项、阻塞与下一里程碑，保留结果链接和复盘日期。
6. 每次实际推进必须追加开发事件，带实际时间、结果、产出入口与 Tasks 关系；任务当前状态的更新不能代替事件历史。

这套结构参考 [Notion 官方 AI 项目更新示例](https://www.notion.com/help/guides/automate-project-updates-and-reporting-with-custom-agents)。未来启用后台 Agent 时需要配置权限、触发条件与活动检查；当前不宣称这些已启用。

## 桌面胶囊

常态只显示图标：Codex、账本以及项目头像。所有名称、百分比、Token 与管理信息在鼠标悬停或点击后显示；点击固定详情，Esc 或外部点击收起。

液态玻璃、Pulse 暗色、经典白色三种样式都保留，由用户选择。项目外环显示本周 Token 占比；内环及细进度条使用 Notion 中明确维护的完成进度。AI 从完整愿景的里程碑权重、产出和验收估算百分比，保留依据与评估时间，不再以 Tasks 比例回退。无评估只有轨道，不假装零进度。

项目头像使用 Notion 页面自身的 icon。应用新建项目时要求 emoji 或 HTTPS Logo；绑定已有项目时验证图标。Notion 自身没有“项目 icon 必填”约束，其他客户端仍能创建无图标页面。图标之后被删除时显示文件夹符号和补充提示，保留计量与绑定。

项目悬停短卡展示状态、下一步、完成进度、本周 Token 占比。点击后分三页：概览为状态、愿景、完成进度和占比；行动为完整当前目标、人工事项计数、极简最新产出与进展；投入为本周／今日 Token、占比和估算投入。Codex 和本期 Token 各为四行数据的单页，所有入口采用行式布局。标签整块可点，卡内无滚动条；小屏或长内容用分页。

胶囊前两个入口固定为 Codex 账号和本期 Token；后面最多四个项目位从 Notion 管理项目中按真实本周 Token 降序选取，每次刷新重新排序。零用量管理项目可以补足展示位，同用量按稳定身份排序；其他管理项目及未纳入管理的本机目录归入「其他」。没有可用管理项目时回退本机有用量文件夹前四项。只调整展示，全部保留日志的 Token 和有用量文件夹任务数仍完整计入。完整管理列表仍包含本周无用量项目，未关联本机记录的项目保持未关联。Notion 项目管理信息与计量列表分别维护，不改变总数或占比分母。

Codex 当前周剩余直接来自官方读数，不是已用数。自然周累计已用独立记录，早重置或跨窗口可能超过 100%。估算投入采用用户选择的 `100%=5 美元` 基准：总投入为自然周已用百分比乘以 5 美元，项目投入再乘该项目本周 Token 占比。这是订阅成本分摊估算，不是实际账单或 API 价格；观测不完整时保持未知或下限，不能为了显示金额把未知写成零。

## 周记录、月核算与独立额度页

用户已确认三种边界：项目周报使用上海自然周；会员月核算使用经确认的续费锚点；官方额度使用服务返回的真实窗口。周、月直接对同一批已接受用量分组，不把整周加成月份，也不将 Token 换算成官方额度。

本轮不新增独立额度页面，保留已经存在的周期配置；导入项目不创建周期库或 Projects 关系。项目工作台以目标、行动、成果和附属每日投入为主。原始日志与高频额度观测留本机，Notion 只记录绝对摘要；计数／质量不变时不因扫描时间推进而反复写。月核算使用每位用户自行确认的续费锚点；只知道日期时按上海午夜划界，标明日粒度估算，不证明历史支付时刻。

具体边界、月底规则、同步审计与历史覆盖见 [周期核算机制](period-proposal.md)。
