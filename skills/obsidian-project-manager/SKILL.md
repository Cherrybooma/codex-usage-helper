# Obsidian 项目管理

## 入口与身份

复用既有中央库和规则，不另建第二套系统：

- 管理库默认 `~/Documents/项目管理obsidian`，或明确配置的 `PROJECT_PM_VAULT`。
- 规则默认 `~/Documents/项目管理系统/规则`，或 `PROJECT_PM_RULES_ROOT`。先读 `AI项目管理约定.md`、`数据约定.md`；模板继续复用同系统目录的 `模板/`。
- 程序与计量数据使用**当前用量小助手工程**，本机默认 `~/Documents/用量小助手/codex-usage-scanner`。先核实其中 `pm`、`widget/project_manager.py`、`widget/markdown_store.py` 存在；安装位置不同时使用用户指定或已验证的源码根目录。不要将正在管理的业务项目目录误作程序根目录，也不要继续调用参考副本“项目管理系统”的程序。

执行该工程 `./pm --help` 与所需子命令帮助确认参数。全局 `--vault`、`--data-dir` 放在子命令前。计量与发布使用应用原有 `widget/data`，不从副本覆盖数据或重新生成 dataset/项目身份。

按项目卡固定 `id` 和实际工程路径定位，先读取最新项目、当前阶段任务、人工事项、近期关键历史与成果。已有绑定或卡片直接复用；同名不是身份。遇到对应关系不明确、重复 ID 或不同路径冲突，保留原资料并列出待核实关系，不为避开冲突新建第二个项目。普通讨论不会自动创建项目。

## 整理与推进

用户授权接入已有项目时，从其说明、实际实现、版本和成果核实目标与现状。先检查中央库已有身份及工程绑定；缺少记录时使用管理命令补一次，并绑定胶囊。必要的新项目用 `pm new-project --existing`，先看帮助并明确工程根目录，不能把中央库或系统支撑目录当业务工程。

项目卡遵循中央规则的总目标、需要决策、需要验收、目前要做的事；当前只细化本阶段，后续阶段留完整计划。原人工正文、既有身份和历史保留，修改前重新读取版本，使用管理命令或遵守其锁、revision 与 digest 的局部更新。未知日期和费用留空；完成度按下节主动评估。

本轮工作完成后，局部维护任务、当前状态和下一步，写明实际做成什么与未验证部分。普通界面微调在同一任务内处理，不逐条建事件；重要成果、范围决定、承诺变化或正式交接才合并一条关键历史。计量刷新不生成开发历史。

## 进度估计必须维护

**进度估计是项目整理的必做项，不是可选装饰。** 接入项目、完整整理现状，以及重要进展收尾时，都要检查并维护整体完成度；项目资料可读取时，必须给出 0–95 的 AI 数值估计。不能以“无法精确计算”“可能不准确”“未完成真机验收”或“这件事不重要”为由省略，现有空值也要补上。这里要求的是有依据的 AI 粗估，不是准确预测剩余工时。已经有明确人工评估或项目整体完成确认的，保留其真实来源与适用范围。

- 先固定评估针对的当前版本目标和验收范围，说明做到什么才算项目整体完成。按已有计划中少量主要成果、实际实现和检查结果判断完成情况，按它们对目标的重要性合成估计；同一范围内保持评估口径与权重相对稳定。发布、真实设备检查和人工验收如属于目标，也计入尚未完成的部分；不能只看代码是否写完，不按任务条数或 Token 消耗换算，也不将五阶段机械地各算 20%。
- 资料不齐时，依据已能读取的说明、代码、版本和成果给出合理粗估，说明采用了什么假设、哪些部分仍不确定；不要因此停止评估或编造测试、验收事实。默认按约 5% 或 10% 粒度表达，避免没有依据的精细数字；已有明确计算依据的整数估计可保留。必要时在说明中给出大致范围，例如“约 60%，大致在 50%–70%，手机后台运行尚未验证”，AI 给出的整体估计与区间上界均不超过 95%。
- 写入既有字段：`progress` 为数值，`progress_source: ai`，`progress_reviewed` 为本次实际评估时间，`progress_evidence` 为简短依据或已有资料链接。依据用日常语言说清已经做成什么、还缺什么和主要不确定项；复用现有项目说明，不为每次评估另建报告。
- 指出最可能改变估计的关键未知问题，以及哪项小检查最有助于确认。需要新证据时优先安排针对性验证；不要求仅为填百分比重跑整套测试，也不把尚未执行的检查写成已通过。
- 在主要成果完成、发现重要问题、目标范围变化或收到验收结果时复核，确实重估才更新数值、依据与评估时间；普通小修或没有新证据时不机械改数，不只刷新日期让旧数看起来是新评估。允许下调，简短说明新问题或范围变化；不能为了维持上涨而沿用失效判断。范围变化时明确新估计针对什么，保留旧范围的真实验收结论。
- **AI 估计最高 95%；100% 只由人明确确认项目整体完成。** 95% 是上限，仍要按证据判断，不能因代码写完、自动测试通过或自认为已达到要求就一律填满。用户只通过一个按钮、单项任务或某轮阶段审阅，不等于确认整个项目完成；不能通过自动关闭任务、改项目状态或将来源改成 manual 绕过此边界。
- 只有用户明确确认当前约定范围的项目整体完成，AI 才可代为登记 `progress: 100`、`progress_source: manual`，保存确认时间、真实原话与来源，并关联对应范围和成果版本。表达是否针对整个项目确实不清楚时再核实；用户已明确确认时直接记录，不重复索要批准。已有真实人工完成确认不在普通接续时改回 AI 估计。复核旧 AI 数值超过 95% 且没有人工整体完成确认的，按现有证据调整至不超过 95%，保留原依据和更正说明，不改写旧历史。
- 0% 表示尚未开始完成目标，不用来代替未知；百分比不代表已经花掉或还需多少工时。即使估计为 80%，也不能据此推算剩余时间为原工时的四分之一。
- 只有实际无法读取项目资料、权限不足或项目身份尚未确定等执行阻塞，才可暂不写入；必须说明具体阻塞和恢复办法，不将一般不确定性当作阻塞。收尾检查数值、来源、依据和日期是否齐全，并简短告知本次估计或沿用情况。

## 成果与人工意见

用 `register-artifact` 登记实际工程内产出或 HTTPS 地址，保留标题、版本、摘要和验证范围；原文件留在工程。进展关联同一正式成果入口，不能只有“完成开发”的结论。Mac 本机路径标明仅 Mac 可用，不冒充手机可访问地址。

正式验收或决定绑定用户真实表达、来源、任务版本与内容摘要；先用 `submit-feedback` / `apply-feedback` 的帮助确认参数。AI 自测、未反对、已读和用户未回复均不是通过。用户已经明确决定的事项落实并留一次依据，不再让人重复批准。

## 胶囊与投入

桌面读取中央 Markdown 的图标、状态、目标、下一步、人工事项和成果；确认本机路径已绑定到正确固定 ID，再检查胶囊缓存。仅写入笔记不等于绑定已完成。项目本周无用量时不伪造 Token，不为占据前四展示位固定排名。

Token 只来自当前工程计量后台；不要从文稿、对话或清单手填消耗。唯一账本发布入口是当前工程 `widget/widget_backend.py --sync-markdown`，保留稳定键与绝对更新；不同来源、每日、周和月不可重复累加。项目管理只操作已配置的本机 Markdown 库，不将历史云端迁移资料作为新的写入目标。

本 Skill 按调用执行，不启动常驻 AI、远程服务、定时任务或新发布流程。收尾说明更新了哪些真实资料、成果与绑定是否可读、已检查范围和待确认事项；不把管理更新当成项目已验收。
